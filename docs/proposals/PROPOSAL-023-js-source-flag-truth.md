## 2. 三个选项

- **A 拆成两个旗标**：`isJs` 保持"整源 JS（`mainJs`）"，另加一列"规则含 JS 方言"，界面那行改成后者（本机 2,105）。
  代价：`source` 表加一列 + **一次性回填**（扫 5,574 行 payload；同族形状已有先例：`Database.collapseLegacyCookieJar`）。
  回填成本不是问题（那份语料脚本读 27 MB + 逐份扫全部字符串，本机 **0.64 秒**跑完）。
  还有一条纪律要顺手立：**"规则含 JS"的判据必须与运行时同源** —— 现在同一件事有三份各写一遍
  （`RuleRunner.isJsRule`、`ContentProcessor.kt:126`、`RuleValue.isJsExpression`），再加第四份必漂。
- **B 整条 `mainJs` 线拿掉**（连同 `JsSourceRunner` 与四处派发、`isJs` 列）。
  依据是根 `AGENTS.md`「不保留向后兼容性，删过时路径而不是加兼容层」。
  **但我不推荐**：它有 4 份测试覆盖、是"书源自带一个 JS 脚本自己组装结果"这种写法的显式支持，
  真实语料里没有 ≠ 生态里永远没有；删它省不了什么，却把一条已实现的能力关掉。
- **C 只把界面上量错的东西改掉**（推荐先做这一半）：
  ① 删掉「JS 书源」那一行统计与那颗标签（恒 0 的数字比没有数字更坏 —— 它暗示"你的库里没有 JS 源"，
  而真相是 37.8% 的源在用 JS 规则）；② 两处分组兜底改成只说「未分组」；
  ③ `isJs` 与 `mainJs` 那条线**留在服务端**（调试器与编辑器仍按 `mainJs` 现读，语义不变）。
  代价最小、不需要迁移，并且**不留下一个说谎的界面**。

**建议顺序**：先 C（一次前端改动，能演、能钉），A 作为后续（真想要"规则含 JS"这个数的时候再加列 + 回填）。
